# AI 개발 하네스 운영 원칙

> 적용: Codex CLI / Claude Code CLI · 기준일: 2026-10-16

이 문서는 AI가 작업을 이해하고, 구현·검증·인계하는 방법을 정의한다. 최소 구성은 **프로젝트 지침 + 프로젝트 설정 + 작업 정의 + 실제 검증 명령 + 변경 이력**이다. 도구별 적용은 [Codex](README-Codex.md), [Claude Code](README-Claude.md), 설치는 [INSTALL.md](INSTALL.md)를 따른다.

## 적용 단위: 프로젝트

이 하네스는 선택한 Git 프로젝트 루트에 설치하고 그 프로젝트에서 검토한다. CLI 실행 파일과 로그인은 사용자 환경의 사전 조건이며, 버전·로그인·전역 진단이 정상이어도 프로젝트 설치 완료로 보지 않는다. 이 문서 묶음의 배치만으로도 설치가 완료되지는 않는다.

| 구분 | 프로젝트에 둘 파일 | 처리 기준 |
| --- | --- | --- |
| 공통 규칙 | `README.md` 및 도구별 운영 문서 | 기존 문서를 보존하며 필요한 내용만 병합 |
| Codex 선택 시 필수 | `AGENTS.md`, `.codex/config.toml` | 프로젝트 지침·설정으로 설치 후 새 세션 검증 |
| Claude Code 선택 시 필수 | `CLAUDE.md`, `.claude/settings.json` | 프로젝트 지침·설정으로 설치 후 새 세션 검증 |
| 사용자 사전 조건 | CLI 실행 파일·인증·홈 디렉터리 전역 설정 | 프로젝트 설치에서 생성·변경·제거하지 않음 |

여기서 필수는 이 하네스의 도입 기준이다. CLI 자체가 해당 파일 없이 실행되지 않는다는 뜻은 아니다. 프로젝트 설정은 사용자·관리자 설정을 자동 배제하지 않는다. 설정 출처와 실효 값을 검토하고, 민감정보가 없는 프로젝트 공용 파일은 버전 관리한다. 개인 설정·계정 상태는 저장소에 복사하지 않는다.

설치 보고는 **사전 조건 / 프로젝트 파일 적용 / 새 세션 검증 / 미해결**로 구분한다. 읽기 전용 경로, 신뢰 상태, 상위 정책 때문에 프로젝트 필수 설정이 적용되지 않으면 미완료로 보고한다. 사용자 수준 변경으로 대신 해결하지 않는다.

## 1. 역할과 정본

| 대상 | 역할 |
| --- | --- |
| 이 README | 공통 운영 규칙의 정본 |
| `AGENTS.md` / `CLAUDE.md` | 도구가 읽는 짧은 진입 지침. 공통 규칙의 위치와 시작 절차를 연결 |
| Git 저장소 | 코드·프로젝트 문서·변경 이력 |
| GitHub Issues | 개별 작업의 목표·완료 조건·현재 상태·블로커 |
| PR·CI·배포 시스템 | 검토·테스트·배포의 실제 증거 |
| Linear | 주요 성과·일정·차단사항·결정을 사람이 이해하도록 요약하고 원본 링크 연결 |

같은 사실의 편집 가능한 정본은 하나만 둔다. Linear에 개별 이슈 상태를 다시 수동 관리하지 않는다. MCP는 접근 수단이며 정본이나 권한 정책을 대신하지 않는다. 연결되지 않은 도구를 사용했다고 주장하지 않는다.

## 2. 문서 위치

최초 설치 시 프로젝트 루트에 아래 표의 `docs/`와 다섯 하위 폴더를 생성한다. 재설치에서는 기존 폴더와 파일을 보존하고 누락된 폴더만 만든다. 문서 파일과 `docs/README.md`는 필요할 때 작성하며, 문서 목록에는 실제 파일만 연결한다. 생성·확인 명령은 [설치 가이드 3절](INSTALL.md#3-공통-문서-배치)을 따른다.

| 위치 | 보관할 내용 |
| --- | --- |
| `docs/` | 주요 요구사항·설계·운영 문서. 필요할 때만 `docs/README.md`를 두고 실제 문서 링크를 모은다 |
| `docs/plans/` | 복잡한 작업의 계획·설계. 상태와 수정일 표시. 작은 작업은 이슈의 짧은 계획으로 대체 |
| `docs/jobs/` | 작업한 날의 결과·검증·미해결·다음 행동. 기본 파일명 `YYYY-MM-DD.md` |
| `docs/guides/` | 설치·실행·검증·배포·장애 대응 등 반복 절차 |
| `docs/references/` | 외부 기술 조사. 출처·확인일·적용 버전 표시 |
| `docs/images/` | 문서용 화면 캡처·구조도. 서비스용 이미지는 기존 앱 자산 경로 사용 |

공통 규칙을 문서마다 복사하지 않는다. 과거 작업일지는 당시 기록이며 현재 상태를 대체하지 않는다. 채택한 결정과 실제 절차가 바뀌면 해당 최신 문서를 함께 갱신한다.

## 3. 작업 계약과 실행 흐름

작업 입력에는 **목표 / 범위·비목표 / 완료 조건 / 검증 방법**을 둔다. 요구사항을 읽어도 결론을 바꾸는 핵심 정보가 없으면 질문하고, 사소한 선택은 가정을 명시해 진행한다.

| 단계 | AI의 행동 | 남길 근거 |
| --- | --- | --- |
| 시작 | 적용 지침, 이슈, 현재 브랜치, 기존 변경, 관련 코드만 확인 | 작업 ID와 시작 상태 |
| 계획 | 최소 변경과 검사 방법을 정함. 복잡한 작업만 별도 계획 | 이슈의 계획 또는 계획 문서 링크 |
| 구현 | 기존 패턴·도구 재사용. 범위 밖 수정과 사용자 변경 덮어쓰기 금지 | 변경 파일·diff |
| 검증 | 관련 검사 실행 후 요구사항·회귀·오류 처리 검토 | 대상 버전·명령·실행 위치·결과 |
| 인계 | 상태와 관련 문서를 갱신하고 미해결·다음 행동 기록 | PR·CI 링크와 작업일지 |

한 작업은 한 세션에서 이해·구현·검증 가능한 크기를 우선한다. 주 에이전트 하나로 시작하고, 독립적인 입력·출력·검증 조건이 있는 경우에만 위임을 검토한다. 같은 파일을 여러 에이전트가 동시에 수정하지 않는다.

## 4. 검증과 완료

검사 명령은 실제 프로젝트의 스크립트·빌드 설정·CI에서 확인한다. `npm test` 같은 명령을 임의로 전제하지 않는다. 도입 시 아래 연결표의 미설정 항목을 실제 경로·명령으로 바꾼다.

| 항목 | 이 프로젝트의 정본 | 적용 상태 |
| --- | --- | --- |
| 요구사항 | [Codex 설치 작업 계약·현재 상태](docs/jobs/codex-install-state.md) | 로컬 작업 ID로 추적. 지정 Issue·PR·CI 없음 |
| 검증 명령·실행 디렉터리 | [검증 가이드](docs/guides/verification.md) · `/home/kwh8121/projects/test` | 파일·설정·Git·문서 배치 검사 PASS. 새 세션 설정 진단 FAIL, 동작 검사 NOT RUN; 상세 내용은 작업 기록 참조 |
| 배포·복구 절차 | [설치 가이드 7절](INSTALL_CODEX.md#7-완료-보고와-되돌리기)과 [실제 변경·백업 기록](docs/jobs/codex-install-state.md) | 앱 배포 N/A. 프로젝트 파일만 기록된 범위에서 복구 |

- 버그는 재현 근거를 확보하고 가능한 경우 회귀 테스트를 추가한다. 기능은 핵심 성공·실패 경로를 검사한다.
- 문서·설정은 링크·구문·실제 적용 조건 등 변경에 맞는 검사를 선택한다.
- 검사 결과는 `PASS / FAIL / NOT RUN / N/A`로 구분한다. 미실행·미적용에는 이유를 적는다.
- 필수 검사 실패·미실행을 통과로 표시하지 않는다. 예외는 결정권자의 사유·잔여 위험·후속 조치를 기록한다.
- 검토는 범위·요구사항·회귀·보안·복잡도를 확인한다. 자체 검토는 독립 리뷰로 표시하지 않는다.
- 선택한 도구의 프로젝트 지침·설정 파일과 새 세션의 로딩·실효 권한·작은 로컬 작업을 모두 검증한다. `claude doctor` 같은 CLI 진단만으로 프로젝트 검토 완료를 표시하지 않는다.
- 구현 완료·검증 완료·배포 완료를 구분한다. 배포 결과는 실제 시스템에서 확인한다.

완료 보고는 **변경 결과 / 검증 근거 / 남은 제약 / 다음 행동(있을 때)**으로 끝낸다. 긴 로그는 복사하지 않고 링크를 연결한다.

## 5. 권한과 실행 환경

- 작업 공간의 가역적인 수정과 허용된 검사는 승인 범위 안에서 진행한다.
- 원격 push·merge, 운영 배포, 파괴적 DB 변경, 비밀값 접근, 외부 서비스 변경, 대규모 삭제는 사전 위임 또는 해당 행위의 사람 승인을 확인한다.
- 지침 파일에 적은 승인 규칙은 기술적 차단 장치가 아니다. 실제 통제는 도구의 권한 설정, 서버 측 접근 권한, 브랜치 보호와 CI 등에서 적용한다.
- 비밀값은 문서·코드·이슈·로그에 남기지 않는다. 민감 설정은 허용된 비밀 관리 수단을 사용한다.
- 도구 장애 시 미확인 범위를 기록한다. 확인할 수 없는 외부 변경만 보류하고 독립적인 로컬 작업은 계속한다.

## 6. Git 이슈·PR·태그

추적 가치가 있는 변경은 이슈에 목표·완료 조건을 기록하고 PR을 연결한다. 이슈·PR 라벨은 **실제 변경 영역 + 작업 유형**으로 관리한다.

| 구분 | 라벨 기준 |
| --- | --- |
| 영역: 필요한 만큼 | `area:frontend` 화면·브라우저 / `area:backend` 서버·API / `area:database` 구조·쿼리 / `area:infra` 빌드·배포·환경 / `area:docs` 문서 |
| 유형: 하나 | `type:feature` 기능 추가 / `type:bug` 오류 수정 / `type:improvement` 기존 기능·성능·구조 개선 / `type:maintenance` 의존성·설정·문서 정비 |

PR은 실제 diff를 기준으로 라벨을 정한다. 라벨 때문에 작업을 분리하지 않는다. Git 태그는 릴리스·검증된 기준 버전에 사용하며, 공유한 태그를 다른 커밋으로 옮기지 않는다.

## 7. 재개와 하네스 개선

작업일지에는 `작업·브랜치·커밋 / 결과 / 검증 / 미해결 / 다음 행동 / 관련 링크`만 남긴다. 같은 날 병렬 작업은 작업별 문서로 나누거나 한 담당자가 취합해 일지 충돌을 줄인다.

재개 시 현재 이슈와 코드 상태를 확인한 뒤 필요한 과거 기록만 읽는다. 전체 문서·과거 로그·모든 MCP를 매번 로드하지 않는다.

반복 실패는 원인에 맞는 한 계층만 우선 개선한다: 요구 오해는 지침, 정보 누락은 문서, 회귀는 테스트, 잘못된 실행은 권한·도구, 인계 누락은 상태 기록을 고친다. 반복 업무가 확인될 때만 Skill·Hook·전문 에이전트를 추가한다.

이 문서는 운영 설계 권장안이다. 자동 로딩·설정·설치 범위의 차이는 도구별 문서와 설치 가이드에 출처를 표시했다. 파일을 배치하는 것만으로 MCP 연결·검사 실행·승인 차단·CI가 설치되지는 않는다.
